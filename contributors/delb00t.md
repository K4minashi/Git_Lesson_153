Парсинг «руинеров» в League of Legends: Как автоматизировать поиск токсичных игроков и деструктивных игровых паттернов
League of Legends (LoL) — одна из самых популярных и одновременно токсичных соревновательных игр в мире. Каждый, кто заходил в ранговые матчи, сталкивался с ними: игроками, которые намеренно «фидят» (умирают по кд), уходят в AFK после первой крови, продают все предметы или просто спамят пингами и токсичным флудом в чат. В комьюнити таких игроков называют руинерами (от англ. ruin — разрушать).
Официальная система репортов Riot Games не всегда работает оперативно, а система трибунала давно в прошлом. Что делать, если вы хотите создать собственный аналитический сервис, трекер «черных списков», дискорд-бота для предупреждения команды во время драфта (лобби) или просто собрать датасет для исследования токсичности?
Ответ один — парсинг данных (Scraping & API Fetching). В этой статье мы подробно разберем, как устроена архитектура сбора данных о руинерах, какие метрики выдают деструктивное поведение и как реализовать такой проект технически.

1. Архитектура получения данных: Riot API vs Клиентский Лог

Для сбора информации о матчах и поведении игроков есть два основных пути, в зависимости от ваших целей (анализ прошедших матчей или оценка игроков прямо во время выбора чемпионов).

Путь А: Официальный Riot API (Riot Developer Portal)

Это самый надежный и легальный способ собирать глобальную статистику. Вам нужно зарегистрировать аккаунт разработчика и получить API-ключ.
• Сущности API:
	• SUMMONER-V4: Получение ID игрока по его Riot ID (Tagline).
	• MATCH-V5: Получение истории матчей (/by-puuid/{puuid}/ids) и детальной информации о конкретном матче (/{matchId}).
	• MATCH-V5 Timeline: Поминутная хроника матча (/{matchId}/timeline). Это ключевой инструмент для поиска руинеров.

Путь Б: LCU API (League Client Update API)

Если ваша цель — создать софт, который предупреждает вас о руинере прямо в лобби (выборе чемпионов), официальный Riot API не поможет (он не дает данные о лобби в реальном времени ради приватности).
В этом случае скрипты подключаются к локальному процессу запущенной игры через протокол HTTPS и WebSocket, используя учетные данные из файла lockfile в папке игры. Это позволяет прочитать никнеймы союзников, как только вы зашли в лобби.

2. Математика токсичности: Какие метрики выдают руинера?

Просто спарсить JSON-ответ от Riot API недостаточно. Руинера определяют скрытые паттерны, которые нужно высчитывать на основе сырых данных. При парсинге матча (MATCH-V5) мы обращаем внимание на следующие маркеры:

1. Метрики «Намеренного фидинга» (Intentional Feeding / Soft Inting)

• KDA (Kill/Death/Assist Ratio): Самый банальный маркер. Если у игрока средний KDA за последние 20 игр ниже 1.0, это повод задуматься.
• Доля в смертях команды: Если команда умерла 30 раз, а конкретный игрок — 18 раз (больше 50%), это явный деструктивный паттерн.
• Таймлайн смертей (из Match Timeline): Настоящий интинг (inting) виден по времени. Если топлейнер умирает на 2-й, 4-й, 5-й и 7-й минутах матча — он, скорее всего, тильтанул и бежит под башню «на автопилоте».

2. Маркеры AFK и «Rage Quit»

• Урон по чемпионам (Damage to Champions): Игрок может не умирать, но просто ходить по карте или стоять на базе. Если у стрелка (ADC) в 30-минутной игре 2000 урона — он саботировал матч.
• Опыт в минуту (XPM) и Золото в минуту (GPM): Падение этих графиков до нуля на определенной минуте в Timeline-логировании четко фиксирует момент, когда игрок «встал в AFK» или вышел из игры.

3. Экономический саботаж (Griefing)

• Продажа предметов: Руинеры часто продают все боевые слоты и покупают 6 слезок (Tear of the Goddess) или 6 ботинок. Спарсив массив items в финальной статистике матча, можно легко отловить этот паттерн.
• Отбирание ресурсов (Farm Stealing): Если поддержка (Support) внезапно с 15-й минуты начинает фармить крипов со скоростью соло-лейнера (смотрим CS в таймлайне), при этом не имея предметов под фарм — это месть своей команде.

3. Техническая реализация: Стек и алгоритм на Python

Для написания парсера чаще всего используется Python благодаря мощным библиотекам для анализа данных и работы с API.

Рекомендуемый стек:

• requests или aiohttp (для асинхронных запросов к API Riot, так как лимиты ключа требуют высокой скорости обработки).
• Pandas (для структурирования данных матчей в таблицы).
• SQLAlchemy / PostgreSQL (для хранения базы данных «подозреваемых»).

Базовый алгоритм работы скрипта-детектора:

1. Сбор пула игроков: Скрипт берет текущий топ ладдера (Challenger/Grandmaster) или базу игроков определенного ранга (например, Emerald IV, где традиционно высокий уровень токсичности).
2. Выкачка истории матчей: Для каждого игрока запрашиваются последние 20-50 матчей.
3. Фильтрация аномалий (Первичный скоринг):
	• Найти матчи, где KDA игрока < 0.5.
	• Найти матчи со статусом gameEndedInEarlySurrender (ранний консид на 3-15 минуте, часто из-за AFK).
4. Глубокий анализ Timeline (Вторичный скоринг):
	• Если обнаружена аномалия, парсится поминутный JSON матча.
	• Высчитывается расстояние между позициями смерти игрока и вражескими башнями (если игрок умирает глубоко под чужой вышкой без союзников рядом — это маркер намеренного фида).
5. Запись в БД: Игроку присваивается «Индекс Токсичности» (Ruining Score). Если индекс превышает условные 75/100, его Riot ID заносится в черный список.

4. Проблемы и вызовы при парсинге League of Legends

Разработчик такого парсера неизбежно столкнется с рядом серьезных препятствий:
• Rate Limits (Ограничения на запросы): Стандартный Development-ключ Riot API дает всего 20 запросов в секунду и 100 запросов в 2 минуты. Для парсинга тысяч игроков этого критически мало. Придется запрашивать Production-ключ, обосновывая полезность своего сервиса для комьюнити, либо выстраивать сложную систему очередей (ограничителей скорости вроде aiolimiter).
• Анонимизация лобби: Riot Games активно борется со сторонними сервисами-трекерами. В последних сезонах они скрыли никнеймы игроков в лобби до начала матча. Теперь узнать, кто с вами играет, через обычный API нельзя — это усложнило жизнь создателям dodge-ботов (программ для отмены матча). Разработчикам приходится искать обходные пути через чтение памяти клиента или LCU API (что технически балансирует на грани нарушения User Agreement).
• Ложноположительные результаты (False Positives): Иногда у хорошего игрока просто «не пошла игра». Он может отыграть со счетом 0/10/2 против смурфа на линии, но он честно старался выиграть. Алгоритм парсера должен уметь отличать плохую игру от намеренного руина. Для этого и нужен анализ логов чата (если доступно через LCU), паттернов закупки предметов и перемещения по карте.

Заключение

Парсинг руинеров в League of Legends — это отличный проект на стыке Data Science и Геймдева. Создание работающей модели, которая по сухим цифрам JSON-логов способна определить человеческие эмоции (тильт, ярость, обиду), требует хорошего понимания макро-игры.
База данных, собранная таким парсером, может стать основой для полезного Discord-бота или веб-сайта (аналога сайтов со статистикой, но с упором на поведенческий фактор), помогая обычным игрокам сохранять свои нервы и MMR, вовремя выходя из лобби с деструктивными тиммейтами.
